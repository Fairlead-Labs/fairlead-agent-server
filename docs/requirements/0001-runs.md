## What it is

The server works an agent's work for a space (a team, or a user's personal
space). Each piece of work is a **session** with owners. A session is
worked in short **runs**: each run is a loop of model calls whose tool calls
go to MCP services as the run's agent. A run that needs a person, a
service's decision or a credential **waits** in Postgres, holds nothing
open meanwhile, and resumes with the outcome as the result of the call
that waited. Each space uses its own model account.

The server has no power of its own. It reaches services only through the
agent's MCP tools, which each service grants per agent; the server's own
checks only narrow what the agent can do. The server never gives an agent:

- a shell, a file system, code execution, a browser or the open web;
- a provider-hosted tool (web search, code execution, remote MCP
  connectors);
- provider-side conversation state;
- a safety rule that lives only in the model's context.

A run's own tools are `read_playbook` and, when the agent may ask,
`ask_person`. The rest of the fixed list about the work (delegating, a
session's state, asking a coordinator, the default memory) is
[requirement 0005](0005-coordinators-and-memory.md)'s.

## Sessions and runs

- **A session** is one agent's work, fixed to the space it was created in,
  under row-level security like every team table. Its owners are users of
  the team; an empty list means the whole team. Owners change by
  compare-and-set.
- **A run** is claimed by compare-and-set: of two claims, one wins, and the
  claim starts its slice. A session has at most one open run; an agent
  works as many runs at once as its cap of active sessions
  ([requirement 0004](0004-agents-sessions-connections.md)), and runs that
  wait do not count, so an agent can carry many sessions that wait on
  people. Due runs start by priority, then due date, then the order they
  were queued.
- **Why a run exists** is fixed when it is made: a trigger, an answer to
  its question, or the continuation of work cut at a limit.
- **States** are the A2A and MCP Tasks names: `queued`, `working`,
  `input_required` (a question, a service's task waiting on a person, a
  runner question), `auth_required` (a credential a person must renew),
  `completed`, `cancelled`, `failed`. What a run waits for is a field
  beside the state. Only `working` spends model tokens, plus a summary
  before a long wait.
- **Steps** are stored in order, each number once.

## The loop

- **Input:**
  - the server's system prompt: the agent, its space, today in the agent's
    time zone, and how tools, held actions and envelopes work;
  - the playbooks' names and descriptions, *Taking on work* in full and,
    when the agent may ask, *Asking a person*, then the agent's own
    playbook;
  - the session's last summary, if a run before wrote one, in an
    `<untrusted-…>` envelope;
  - the triggers the session has not seen, in order: a person's message as
    text, anything else in an envelope;
  - the tools of the agent's services (the host's and the team's own
    connections it holds a credential for), plus `read_playbook` and
    `ask_person`, which the runner answers itself.
- **Each step** is one model call. Its tool calls go to the services, and
  their answers come back with the service's envelopes and marks.
- **A run stops** at a final answer; when it waits; at a limit.
- **Output only through tools,** plus the run's result. The run reaches
  people only through the agent's own tools, each needing its grant, and
  through its final answer, which is the run's result in the API.
- **People steer while it works.** Triggers that arrive while a run works
  (a person's message, the host's news) reach it before its next step;
  those for a waiting run reach it when it resumes.
- **Context.** Tool answers are cut at 20,000 characters. The history is
  append-only. The system prompt and the playbooks are never compacted or
  summarized. Nothing that keeps the agent safe lives in the context, so a
  summary can cost quality but never safety.
- **One model per run.** A conversation never changes provider. A changed
  model profile ends the run (`model-changed`) and the next is a new run.

## Limits

- **Per agent, each allowing *None*.** A new agent starts at 30 steps and
  300,000 input tokens per run and 10 runs per trigger. There is no token
  budget: the money cap is the provider's own spend limit.
- **A run out of steps or tokens** writes its summary and ends
  (`steps-limit`, `tokens-limit`); the work goes on in a new run. Once one
  piece of work has used its runs, its next run waits on a runner question:
  *Continue* allows another round, *Stop* ends it.
- **The 15-minute slice** is the server's own and cannot be *None*. A run
  works 15 minutes (less a minute's margin), then checkpoints and is queued
  again, never ended. A run claimed again goes on from its checkpoint.
- **Provider errors.** A 429 or 5xx queues the run again after the
  provider's `Retry-After`; any other model error fails it. An agent
  without a usable profile fails its run without calling a model
  (`no-profile`).

## Waiting and resuming

- **A question.** `ask_person` keeps the question sealed and lists it to
  the session's owners ([requirement 0004](0004-agents-sessions-connections.md)).
  The run waits in `input_required`; an owner's answer queues it again,
  and the answer is the call's result, with whatever arrived meanwhile.
- **A held action is the service's MCP task.** A service answers a held
  call with a task; the run waits on its id and polls it no faster than its
  `pollIntervalMs`, the interval doubling up to 15 minutes. A task waiting
  on a person at the service puts the run in `input_required`. Its outcome
  is the call's result: the service's result, its failure, or that it was
  cancelled. The server never answers a task's `inputRequests`.
- **A credential.** A service that refuses the agent's credential, and a
  grant that cannot be renewed, put the run in `auth_required` until a
  person gives a new one; then the call is made again.
- **Calls after the waiting one** in the same turn are answered as not run.
- **Silence is not an answer.** A waiting run never goes ahead with the
  agent's own pick.
- **Checkpoints.** Each step is stored before its call; its id is the
  call's step id. The transcript is sealed and saved after each model turn
  and each turn's results. A claimed run continues from its last stored
  step.
- **Nothing is done twice by accident.** A call cut off (the service did
  not answer, or the runner stopped mid-call) is looked up by its step id
  in the host's record of calls (the `RunCallLog` port, where the host
  offers one; a team's own connections never do). Not received, or a
  read: made again, once. A write with a recorded status: told to the
  model. A write without one: a runner question whose *Continue* tells the
  model the outcome is unknown, never repeating it.
- **A summary before the cache goes cold.** The model adapter reports the
  cache window it paid for (5 minutes, or an hour where the profile pays
  for it). When that window ends within 90 seconds and the last model step
  read more than 30,000 input tokens, a waiting run gets one call without
  tools (the tools still declared) that writes the goal, what is done, the
  decisions taken, the facts with the ids they came from, and what the run
  waits for, with the open question word for word. The summary is sealed;
  the waiting call stays as it is. From then on the model sees the first
  message, the summary in an envelope, and the messages from the last
  model turn on. Below the threshold, earlier or once the window has
  closed, there is no summary.
- **Versions.** For every object a read answered about, the run keeps a
  version, never content: the service's own (`version`, `updatedAt`,
  `etag`), else a hash of the answer. After a summary, on resume, the
  runner reads them again as the agent: a changed object's new answer is
  added, a gone or no longer granted one is named, an unchanged one adds
  nothing.
- **The injection mark is runner state.** A result marked
  `injectionSuspected` marks the run for good. A summary travels in an
  envelope and cannot wash the mark out.

## The end of a run

A run that ends at a final answer seals that answer as its **result** and
writes a **summary** for the session's next run (one call without tools).
A trigger that arrived meanwhile queues the next run. Every end is
announced ([requirement 0004](0004-agents-sessions-connections.md), the
host webhook).

## Runner questions

The runner raises a runner question itself, never the model, in cases no
playbook can talk away:

1. the run is marked `injectionSuspected` and the next call would write;
2. the agent makes the same call (name and canonical arguments) a third
   time;
3. a write's outcome is unknown;
4. one piece of work has used its runs.

A **write** is a call of a tool whose annotations lack `readOnlyHint:
true`; a tool without the hint counts as a write, `ask_person` included.
Reads go on while a run is marked. Runner questions go to the session's
owners like the agent's own, answered *Continue* or *Stop*. *Continue* lets
that one call through (an unknown outcome is told to the model, never
repeated); the mark stays, so the next write asks again. *Stop* cancels
the run.

## Playbooks

The grants, and so the tool list, are the only control. Everything here is
guidance.

- **The server's playbooks** live in `playbooks/<name>.<language>.md`, in
  English and German: a title line, a description line, the body. The
  system prompt lists names and descriptions; the model reads a body with
  `read_playbook`, which the runner answers and no service sees. The set:
  *Taking on work*, *Triaging an inbox*, *Replying with a draft*, *Finding
  a meeting time*, *Filing an attachment to a project*, *When an action is
  held*, *Asking a person*.
- ***Asking a person*** is loaded in every run that may ask, at
  *Balanced*: ask when the work leaves out what only a person knows, when
  two readings lead to different results, when a mail or file asks for more
  than the work did, and before anything that commits the team (a promise,
  a price, a date); never ask what the tools can find out; put questions
  together, and always say what you would choose and why. No "Shall I go
  ahead?" about a plain plan: a held action holds it anyway.
- **The agent's own playbook** holds standing instructions for that agent
  ("Invoices go to `Archive/Invoices`; answer in German"), up to 10,000
  characters.
- **Agents write no playbooks.** No tool writes one.

## Model profiles

- **Per space.** A team keeps model profiles for its team agents; a user
  keeps their own for their personal agents
  ([requirement 0004](0004-agents-sessions-connections.md)). A profile
  holds provider, model, region or endpoint, a credential, effort and cache
  window. Each agent names at most one; a profile an agent names cannot be
  removed.
- **The space's own account.** A profile names its own API key, or the
  team's own cloud account:
  - an API key is sealed under the team's key and write-only: never in an
    answer, a log line or a record;
  - a cloud account is reached as the team's own identity, with no stored
    key: a Google service account per team (`ag-` and the first 27 hex
    characters of the SHA-256 of the team id, in `TEAM_IDENTITY_PROJECT`),
    which the server impersonates through IAM Credentials for Vertex AI,
    and whose ID token assumes an AWS role (STS) for Bedrock and signs in to
    Entra for Azure OpenAI. The team grants that identity access in its own
    project, role or app. A profile naming another team's account fails
    there. Tokens are cached per team until a minute before they expire.

## Adapters

- **One interface.** `ModelClient.complete` takes system blocks, messages
  and function tools, and answers ordered parts (text, tool calls,
  reasoning), a stop (`end`, `tool_calls`, `refusal`, `cut_off`), usage
  (input, cache read, cache write, output) and the cache window it paid for.
- **Two wire formats** over `fetch`: Anthropic Messages (the Claude API with
  an API key; Vertex AI by `rawPredict` with the team's token; Bedrock by
  InvokeModel signed with the server's own SigV4) and OpenAI Responses
  (OpenAI with an API key; Azure OpenAI by its v1 path with a key or an
  Entra token).
- **Reasoning state** travels as opaque provider blocks, sent back unchanged
  only to the same format and model; another model's reasoning is dropped.
- **Call ids.** The runner mints its own; the provider's pairs results back.
  A call the provider did not make gets an id in `^[a-zA-Z0-9_-]{1,64}$`. A
  result without its call is never sent.
- **Caching.** Anthropic gets explicit breakpoints on the system's last
  block and the last two user messages, five minutes or an hour per
  profile; OpenAI gets a `prompt_cache_key` and an assumed five minutes.
- **Effort.** Anthropic's `output_config.effort` (no `thinking` parameter);
  OpenAI's `reasoning.effort`, `max` sent as `xhigh`.
- **OpenAI requests** always carry `store: false`, ask for encrypted
  reasoning back, and declare non-strict function tools.
- **Errors.** No retries in the adapters: a 429 or 5xx surfaces with its
  `Retry-After`, and the runner decides. An error names the status and the
  provider's type, never a credential. Calls are not streamed.
- **Nothing hosted, nothing forced, nothing stored.** A function tool has a
  name, a description and a schema, and the types cannot express a hosted
  tool or a forced tool choice; `none` exists only for the summary's call.
  No request relies on provider-side state: each step sends the whole
  conversation.
- **One conformance suite** runs every adapter against in-process fake
  provider servers (`src/testing/`) that enforce each format's rules.

## Transcripts

The transcript holds what the agent read and wrote. It is sealed under the
team's key, with the summary, the result and the triggers' bodies, opens
only for its team and run, and is purged when the run ended longer ago
than the team's retention (the directory's `retention_days`, 30 days when
none is set; requirement 0003, *Retention*; the scheduler's hourly pass); the run's facts (cause, model, steps, tokens,
stop reason) stay.

## Later
